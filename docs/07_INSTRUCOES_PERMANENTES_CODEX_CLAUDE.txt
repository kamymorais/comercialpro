# COMERCIALPRO — INSTRUÇÕES PERMANENTES PARA CODEX / CLAUDE

Este arquivo deve ser lido antes de qualquer alteração no projeto.

======================================================================
1. OBJETIVO DO PROJETO
======================================================================

Construir uma aplicação web leve, moderna, mobile-first e instalável como PWA, para controle diário de previsão de pagamento por consultores, gerentes e gerente regional.

A aplicação deve ser simples, mas bem estruturada.

Não criar complexidade desnecessária.

3. DIRETRIZES DE CODIFICAÇÃO
======================================================================

Sempre:

- Trabalhar em etapas pequenas.
- Explicar o que será alterado.
- Evitar quebrar fluxo existente.
- Criar componentes reutilizáveis.
- Separar regra de negócio da interface.
- Validar permissão no servidor.
- Usar TypeScript corretamente.
- Usar nomes claros.
- Evitar gambiarras.
- Evitar duplicação de código.
- Manter estrutura simples.

Nunca:

- Expor DATABASE_URL.
- Expor senha do banco.
- Expor API key.
- Usar NEXT_PUBLIC em secret privado.
- Salvar senha pura.
- Enviar passwordHash para o frontend.
- Deixar gerente acessar consultor de outro gerente.
- Deixar consultor acessar dados de outros.
- Deixar usuário pendente acessar dashboard.
- Apagar histórico no reset.
- Criar dependências pesadas sem necessidade.
- Criar arquitetura exagerada.

======================================================================

Todos os valores devem ser tratados como Decimal no banco.

Campos:

- insuranceValue.
- tcValue.

Exibição:

- Formatar como moeda brasileira.
- Exemplo: R$ 1.250,00

Entrada:

- Aceitar digitação simples.
- Normalizar no backend.
- Nunca confiar apenas no frontend.

7. PADRÃO DE AUTORIZAÇÃO
======================================================================

Permissões obrigatórias:

ADMIN:
- Tudo.

REGIONAL_MANAGER:
- Gerentes e consultores visíveis.

MANAGER:
- Apenas consultores vinculados.

CONSULTANT:
- Apenas a própria previsão.

Toda operação sensível deve validar:

- Usuário logado.
- Status APPROVED.
- Role correta.
- Vínculo correto.

======================================================================
8. PADRÃO DE RESET
======================================================================

O reset diário às 19h deve funcionar pela data operacional.

Não apagar dados.

Fluxo recomendado:

- getOperationalDate() retorna a data correta do ciclo.
- Antes das 19h, retorna data atual.
- Depois das 19h, retorna próxima data.
- Como nova data não tem previsões, os totais aparecem zerados.
- ResetLog registra execução.

A rota cron deve ser protegida por CRON_SECRET.

======================================================================
9. PADRÃO DE SESSÃO
======================================================================

Sessão:

- Expira em 3 horas.
- Cookie HTTP-only.
- Token aleatório.
- Token salvo com hash no banco.
- expiresAt controlado no banco.

Ao validar:

- Se não existe sessão, bloquear.
- Se expirou, bloquear.
- Se revokedAt existe, bloquear.
- Se usuário não está APPROVED, bloquear.

12. TESTES MANUAIS OBRIGATÓRIOS
======================================================================

Antes de considerar pronto, testar:

1. Admin faz login.
2. Consultor solicita cadastro escolhendo gerente.
3. Gerente solicita cadastro sem escolher gerente.
4. Regional solicita cadastro sem escolher gerente.
5. Admin aprova consultor.
6. Admin aprova gerente.
7. Admin aprova regional.
8. Consultor envia previsão.
9. Gerente vê consultor.
10. Gerente edita consultor.
11. Gerente não vê consultor de outro gerente.
12. Regional vê gerentes.
13. Regional clica no gerente.
14. Regional edita consultor.
15. Admin vê todos.
16. Sessão expira.
17. Reset muda data operacional.
18. PWA instala na tela inicial.
19. Nenhum secret aparece no frontend.
20. Build final passa sem erro.
