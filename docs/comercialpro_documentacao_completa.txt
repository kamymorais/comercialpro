# COMERCIALPRO — CONTEXTO GERAL DO PROJETO

Projeto: ComercialPro
Tipo: Aplicação web leve, modular e instalável na tela inicial do celular como PWA.
Objetivo principal: registrar e acompanhar previsões diárias de pagamento/produção por consultores, gerentes e gerente regional.

Este documento deve ser lido antes de qualquer codificação por Codex, Claude ou qualquer outro agente de IA.

======================================================================
1. VISÃO GERAL
======================================================================

O ComercialPro será uma aplicação web simples, leve, moderna e bem organizada, pensada para uso diário por equipe comercial.

A aplicação precisa funcionar bem no celular, com visual limpo, moderno, rápido e sem excesso de elementos.

A ideia é que o usuário acesse pelo navegador e salve o sistema na tela inicial do celular, funcionando como app instalado. Portanto, o projeto deve ser preparado como PWA.

A aplicação terá:

- Tela de cadastro.
- Tela de login.
- Aprovação de cadastros pelo administrador.
- Perfis com níveis diferentes de acesso.
- Registro diário de previsão de pagamento.
- Visualização hierárquica por consultor, gerente e gerente regional.
- Reset automático diário às 19h, zerando a prévia do dia operacional.
- Banco Neon/PostgreSQL.
- Stack simples, preferencialmente usando Next.js fullstack.

======================================================================
2. PERFIS DO SISTEMA
======================================================================

O sistema terá quatro tipos principais de usuário:

1. ADMIN
   - Aprova todos os cadastros.
   - Define o perfil de cada usuário.
   - Define vínculo entre consultor e gerente.
   - Pode visualizar tudo.
   - Pode editar tudo.
   - Pode executar reset manual, se necessário.

2. GERENTE_REGIONAL
   - Tem visão dos gerentes.
   - Pode clicar em um gerente e visualizar os consultores daquele gerente.
   - Pode clicar em um consultor e editar a previsão dele.
   - Visualiza a prévia total geral da sua visão.

3. GERENTE
   - Visualiza apenas os consultores atrelados a ele.
   - Visualiza a prévia total da sua equipe.
   - Pode clicar em um consultor e editar os valores dele.
   - Não visualiza consultores de outros gerentes.

4. CONSULTOR
   - Visualiza apenas sua própria tela de formulário.
   - Preenche diariamente:
     - Valor da produção.
     - Valor do seguro.
     - Valor da TC.
     - Ou marca como "Sem previsão".
   - Envia sua previsão do dia.

======================================================================
3. FLUXO DE CADASTRO
======================================================================

A tela de cadastro deve solicitar:

- Nome completo.
- Usuário de acesso.
- Senha.
- Tipo de solicitação:
  - Consultor.
  - Gerente.
  - Gerente regional.
- Campo de seleção de gerente, somente quando o usuário escolher "Consultor".

Regra importante:

- Se o usuário estiver se cadastrando como CONSULTOR, ele precisa escolher um gerente.
- A lista de gerentes deve puxar apenas gerentes já aprovados pelo ADMIN.
- Se o usuário estiver se cadastrando como GERENTE, ele não precisa escolher gerente.
- Se o usuário estiver se cadastrando como GERENTE_REGIONAL, ele também não precisa escolher gerente.
- Mesmo escolhendo o tipo de solicitação no cadastro, o usuário NÃO define seu próprio perfil final. O ADMIN define na aprovação.
- Todo cadastro novo deve nascer com status PENDENTE.
- O usuário só pode acessar o sistema depois de aprovado pelo ADMIN.

======================================================================
4. FLUXO DE APROVAÇÃO
======================================================================

O ADMIN terá uma tela para ver cadastros pendentes.

Para cada cadastro, o ADMIN poderá:

- Aprovar.
- Rejeitar.
- Definir o perfil final:
  - CONSULTOR.
  - GERENTE.
  - GERENTE_REGIONAL.
- Se for CONSULTOR, validar ou alterar o gerente vinculado.
- Se for GERENTE, aprovar sem necessidade de gerente.
- Se for GERENTE_REGIONAL, aprovar sem necessidade de gerente.

Regras:

- Apenas ADMIN aprova cadastro.
- Usuário pendente não pode usar o sistema.
- Usuário rejeitado não pode usar o sistema.
- Usuário aprovado pode acessar conforme seu perfil.

======================================================================
5. FUNCIONALIDADE PRINCIPAL
======================================================================

A funcionalidade principal é a previsão de pagamento do dia.

O CONSULTOR informa diariamente:

- Valor da produção.
- Valor do seguro.
- Valor da TC.
- Ou marca "Sem previsão".

O GERENTE visualiza:

- Todos os consultores vinculados a ele.
- Valor da produção de cada consultor.
- Valor do seguro de cada consultor.
- Valor da TC de cada consultor.
- Status "Sem previsão", quando marcado.
- Total da equipe.

O GERENTE_REGIONAL visualiza:

- Lista de gerentes.
- Total por gerente.
- Ao clicar em um gerente, visualiza os consultores dele.
- Ao clicar em um consultor, pode editar os valores.
- Total geral da visão regional.

O ADMIN visualiza:

- Tudo.
- Usuários.
- Cadastros.
- Previsões.
- Totais por gerente.
- Totais por gerente regional.
- Total geral.

======================================================================
6. RESET DIÁRIO
======================================================================

Todo dia, às 19h no horário de Brasília/São Paulo, o sistema deve zerar os valores ativos dos consultores.

O objetivo do reset:

- A previsão do dia seguinte deve começar zerada.
- Os totais dos gerentes devem zerar.
- Os totais do gerente regional devem zerar.
- O ADMIN deve ver os valores zerados para o próximo ciclo.

Recomendação técnica:

- Não apagar o histórico.
- Criar registros por data.
- Quando virar o ciclo operacional, a tela deve buscar a previsão da data operacional atual.
- O reset pode criar registros vazios para o novo dia ou simplesmente fazer a busca retornar zero se não houver previsão para o dia.

Importante:

- Manter histórico é melhor do que apagar.
- Se o gerente ou admin quiser consultar dias anteriores no futuro, os dados estarão preservados.
- A operação de reset precisa ser idempotente: se rodar duas vezes no mesmo dia, não pode duplicar nem corromper dados.

======================================================================
7. SESSÃO E LOGIN
======================================================================

O login será simples.

Regras:

- Usuário acessa com usuário e senha.
- Sessão deve expirar após 3 horas.
- Ao expirar, o usuário volta para o login.
- Usar cookie HTTP-only.
- Não expor token em localStorage.
- Não expor dados sensíveis no frontend.
- Senha deve ser armazenada com hash simples, mesmo em ambiente de teste.

Observação:

Mesmo o projeto sendo simples, não colocar senha pura no banco. Usar bcrypt ou argon2 evita problema básico e não aumenta complexidade relevante.

# COMERCIALPRO — STACK E ARQUITETURA RECOMENDADA

======================================================================
1. STACK PRINCIPAL
======================================================================

Recomendação para o MVP:

- Next.js
- TypeScript
- App Router
- Tailwind CSS
- Prisma ORM
- Neon PostgreSQL
- PWA
- Cookie HTTP-only para sessão
- bcrypt ou argon2 para hash de senha

======================================================================
2. POR QUE NEXT.JS FULLSTACK
======================================================================

O projeto precisa ser simples e barato.

Next.js fullstack permite ter no mesmo projeto:

- Frontend.
- Backend.
- Rotas de API.
- Server actions.
- Renderização server-side.
- Integração direta com Prisma.
- PWA.
- Deploy simples.

Isso evita criar:

- Backend separado em Nest.
- API separada.
- Mais de um serviço.
- Mais custo.
- Mais configuração.

======================================================================
3. BANCO DE DADOS
======================================================================

Banco recomendado:

- Neon PostgreSQL.

Motivos:

- Barato.
- PostgreSQL real.
- Combina com Prisma.
- Bom para projetos pequenos e médios.
- Permite evoluir sem trocar stack.

======================================================================
4. ORM
======================================================================

ORM recomendado:

- Prisma.

Motivos:

- Tipagem boa com TypeScript.
- Migrations organizadas.
- Modelagem clara.
- Fácil leitura para Codex/Claude.
- Facilita manutenção.

======================================================================
5. AUTENTICAÇÃO
======================================================================

Autenticação simples, sem sistema pesado.

Recomendação:

- Usuário + senha.
- Senha com hash.
- Sessão em cookie HTTP-only.
- Expiração de 3 horas.
- Tabela Session no banco ou JWT assinado no cookie.

Opção recomendada para simplicidade:

- Cookie com token aleatório.
- Token salvo com hash na tabela Session.
- expiresAt = now + 3h.

Fluxo:

1. Usuário envia username e senha.
2. Backend valida.
3. Backend cria sessão.
4. Backend grava cookie HTTP-only.
5. Middleware valida cookie.
6. Se expirado, remove sessão e redireciona para login.

======================================================================
6. PWA
======================================================================

A aplicação deve funcionar como app salvo na tela inicial do celular.

Configurações necessárias:

- public/manifest.webmanifest
- public/icons/icon-192.png
- public/icons/icon-512.png
- theme_color
- background_color
- display: standalone
- start_url: /
- name: ComercialPro
- short_name: ComercialPro

# COMERCIALPRO — MODELAGEM DO BANCO / PRISMA

======================================================================
1. VISÃO GERAL

Banco: PostgreSQL no Neon.

A modelagem precisa atender:

======================================================================

3. MODEL USER
======================================================================

User representa qualquer pessoa do sistema.

- requestedRole

- insuranceValue
- tcValue
- noForecast
- submittedAt
- updatedById

Regras:

  - consultantId + operationalDate
- Valores monetários devem usar Decimal.
- Se noForecast = true, os valores devem ser tratados como zero.
- updatedById registra quem fez a última edição.

Campos recomendados:

- operationalDate
- executedAt
- status

Regras:

- Se já existir ResetLog SUCCESS para a data, não executar reset novamente.

generator client {

datasource db {
  provider = "postgresql"
  url      = env("DATABASE_URL")

enum Role {

  MANAGER
  CONSULTANT
}

enum UserStatus {
  PENDING
  APPROVED
  REJECTED

enum RequestedRole {
  REGIONAL_MANAGER
  MANAGER
  CONSULTANT

enum ResetStatus {

  SKIPPED
  ERROR

model User {
  id                 String        @id @default(cuid())
  fullName           String
  username           String        @unique
  passwordHash       String
  requestedRole      RequestedRole
  role               Role?
  status             UserStatus    @default(PENDING)

  managerId          String?
  manager            User?         @relation("ManagerConsultants", fields: [managerId], references: [id])
  consultants        User[]        @relation("ManagerConsultants")

  regionalManagerId  String?
  regionalManager    User?         @relation("RegionalManagers", fields: [regionalManagerId], references: [id])
  managers           User[]        @relation("RegionalManagers")

  approvedById       String?
  approvedBy         User?         @relation("ApprovedUsers", fields: [approvedById], references: [id])
  approvedUsers      User[]        @relation("ApprovedUsers")

  approvedAt         DateTime?
  rejectedAt         DateTime?

  sessions           Session[]
  forecasts          DailyForecast[] @relation("ConsultantForecasts")
  updatedForecasts   DailyForecast[] @relation("ForecastUpdatedBy")

  createdAt          DateTime      @default(now())
  updatedAt          DateTime      @updatedAt

  @@index([status])
  @@index([role])
  @@index([managerId])
  @@index([regionalManagerId])
}

model DailyForecast {
  id               String    @id @default(cuid())
  consultantId     String
  consultant       User      @relation("ConsultantForecasts", fields: [consultantId], references: [id])

  operationalDate  DateTime

  productionValue  Decimal   @default(0) @db.Decimal(12, 2)
  insuranceValue   Decimal   @default(0) @db.Decimal(12, 2)
  tcValue          Decimal   @default(0) @db.Decimal(12, 2)

  noForecast       Boolean   @default(false)
  submittedAt      DateTime?

  updatedById      String?
  updatedBy        User?     @relation("ForecastUpdatedBy", fields: [updatedById], references: [id])

  createdAt        DateTime  @default(now())
  updatedAt        DateTime  @updatedAt

  @@unique([consultantId, operationalDate])
  @@index([operationalDate])
  @@index([consultantId])
}

model Session {
  id          String    @id @default(cuid())
  userId      String
  user        User      @relation(fields: [userId], references: [id])

  tokenHash   String    @unique
  expiresAt   DateTime
  revokedAt   DateTime?

  createdAt   DateTime  @default(now())

  @@index([userId])
  @@index([expiresAt])
}

model ResetLog {
  id               String      @id @default(cuid())
  operationalDate  DateTime    @unique
  executedAt       DateTime    @default(now())
  status           ResetStatus
  message          String?

}

======================================================================
8. REGRA DE DATA OPERACIONAL
======================================================================

O sistema zera às 19h.

Existem duas formas:

FORMA SIMPLES:
- Usar a data calendário do Brasil.
- Às 19h, cron marca reset para o dia.
- A partir do reset, novas previsões são da próxima data.

FORMA RECOMENDADA:
- Criar função getOperationalDate().
- Se horário atual for antes de 19h, operationalDate = data atual.
- Se horário atual for igual ou depois de 19h, operationalDate = próxima data.

Exemplo:
- 08/07/2026 18:30 -> operationalDate = 08/07/2026
- 08/07/2026 19:01 -> operationalDate = 09/07/2026

Isso faz o sistema "zerar" sem apagar dados.

======================================================================
9. CONSULTAS IMPORTANTES
======================================================================

Total do consultor:
- Buscar DailyForecast do consultantId na operationalDate atual.

Total do gerente:
- Buscar consultores com managerId = gerente.id.
- Buscar previsões da operationalDate atual.
- Somar productionValue + insuranceValue + tcValue.

Total do regional:
- Buscar gerentes.
- Buscar consultores dos gerentes.
- Buscar previsões da operationalDate atual.
- Somar valores.

Total admin:
- Buscar todos os consultores aprovados.
- Buscar previsões da operationalDate atual.
- Somar valores.

======================================================================
10. OBSERVAÇÃO SOBRE HISTÓRICO
======================================================================

Não deletar DailyForecast no reset.

O reset visual acontece porque a aplicação muda a data operacional.

Esse modelo permite histórico futuro sem retrabalho.

# COMERCIALPRO — REGRAS DE NEGÓCIO E PERMISSÕES

======================================================================
1. REGRA CENTRAL
======================================================================

Cada pessoa acessa com seu próprio usuário e senha.

Cada perfil enxerga apenas o que seu nível permite.

O sistema é baseado em hierarquia:

ADMIN
  -> vê todos

GERENTE_REGIONAL
  -> vê gerentes
  -> vê consultores dos gerentes
  -> edita consultores da sua visão

GERENTE
  -> vê seus consultores
  -> edita seus consultores

CONSULTOR
  -> vê apenas a própria previsão
  -> edita apenas a própria previsão

======================================================================
2. REGRAS DO ADMIN
======================================================================

ADMIN pode:

- Aprovar cadastro.
- Rejeitar cadastro.
- Definir perfil.
- Definir vínculo.
- Ver todos os usuários.
- Ver todas as previsões.
- Editar qualquer previsão.
- Executar reset manual.
- Consultar histórico, se implementado.

ADMIN não deve:

- Ter restrição de gerente.
- Depender de aprovação por outro usuário.

======================================================================
3. REGRAS DO GERENTE REGIONAL
======================================================================

GERENTE_REGIONAL pode:

- Ver gerentes.
- Ver total por gerente.
- Ver consultores de cada gerente.
- Ver previsão dos consultores.
- Editar previsão dos consultores visíveis.
- Ver prévia total regional.

GERENTE_REGIONAL não deve:

- Aprovar cadastro.
- Criar usuário diretamente.
- Alterar perfil de usuário.
- Ver tela admin.

Observação MVP:
- O gerente regional pode visualizar todos os gerentes aprovados.
- Caso no futuro exista mais de um regional com times diferentes, usar regionalManagerId para limitar visão.

======================================================================
4. REGRAS DO GERENTE
======================================================================

GERENTE pode:

- Ver consultores vinculados a ele.
- Ver previsão dos seus consultores.
- Editar previsão dos seus consultores.
- Ver prévia total da equipe.

GERENTE não pode:

- Ver consultores de outro gerente.
- Editar consultor de outro gerente.
- Aprovar cadastro.
- Alterar perfil.
- Ver tela admin.
- Ver tela regional.

======================================================================
5. REGRAS DO CONSULTOR
======================================================================

CONSULTOR pode:

- Ver própria previsão.
- Enviar própria previsão.
- Atualizar própria previsão do dia operacional.
- Marcar sem previsão.

CONSULTOR não pode:

- Ver outro consultor.
- Ver gerente.
- Ver regional.
- Ver admin.
- Editar previsão de outra pessoa.
- Aprovar cadastro.

======================================================================
6. REGRAS DO CADASTRO
======================================================================

Quando uma pessoa se cadastra:

- O status inicial é PENDING.
- O perfil final ainda não está liberado.
- A pessoa não pode acessar área interna.

Se solicitou CONSULTOR:

- Precisa escolher um gerente aprovado.
- O admin pode validar ou trocar o gerente na aprovação.

Se solicitou GERENTE:

- Não precisa escolher gerente.
- Admin aprova como gerente.

Se solicitou GERENTE_REGIONAL:

- Não precisa escolher gerente.
- Admin aprova como gerente regional.

======================================================================
7. REGRAS DA PREVISÃO
======================================================================

A previsão possui:

- Produção.
- Seguro.
- TC.
- Sem previsão.

Total da previsão:

produção + seguro + TC

Se "Sem previsão" estiver marcado:

- Produção = 0.
- Seguro = 0.
- TC = 0.
- Total = 0.
- noForecast = true.

Se houver qualquer valor positivo:

- noForecast = false.

======================================================================
8. REGRAS DE TOTALIZAÇÃO
======================================================================

Total do consultor:

- Soma da própria previsão do dia operacional.

Total do gerente:

- Soma da previsão dos consultores vinculados a ele.

Total do gerente regional:

- Soma dos totais dos gerentes visíveis.

Total do admin:

- Soma das previsões de todos os consultores aprovados.

======================================================================
9. REGRAS DE EDIÇÃO
======================================================================

Consultor:

- Pode editar apenas sua própria previsão.

Gerente:

- Pode editar apenas consultores com managerId igual ao seu id.

Gerente regional:

- Pode editar consultores dentro da sua visão.
- No MVP, a visão pode ser todos os gerentes aprovados.
- Em versão futura, validar pelo regionalManagerId do gerente.

Admin:

- Pode editar qualquer previsão.

Toda edição deve registrar:

- updatedById.
- updatedAt.

======================================================================
10. REGRA DO RESET
======================================================================

O reset acontece diariamente às 19h.

Objetivo:

- Zerar visualmente as previsões do ciclo seguinte.

Não fazer:

- Não deletar histórico.
- Não apagar registros anteriores.
- Não sobrescrever previsão antiga.

Fazer:

- Usar operationalDate.
- Após 19h, a operationalDate muda para a próxima data.
- Como não existem previsões para a nova operationalDate, os valores aparecem zerados.
- Registrar ResetLog.

======================================================================
11. REGRA DE DATA OPERACIONAL
======================================================================

A data operacional é a data usada para as previsões.

Exemplo:

Dia 08/07/2026 antes das 19h:
- operationalDate = 08/07/2026

Dia 08/07/2026 depois das 19h:
- operationalDate = 09/07/2026

Isso permite que a equipe comece a lançar previsão do próximo ciclo após 19h.

======================================================================
12. REGRAS DE STATUS
======================================================================

UserStatus:

PENDING:
- Cadastro enviado.
- Aguardando admin.
- Sem acesso operacional.

APPROVED:
- Cadastro aprovado.
- Usuário pode acessar.

REJECTED:
- Cadastro rejeitado.
- Usuário não pode acessar.

======================================================================
13. PERMISSÕES POR ROTA
======================================================================

/login
- Público.

/cadastro
- Público.

/aguardando-aprovacao
- Público ou usuário pendente.

/admin
- Apenas ADMIN.

/consultor
- Apenas CONSULTANT.

/gerente
- Apenas MANAGER.

/regional
- Apenas REGIONAL_MANAGER.

APIs admin:
- Apenas ADMIN.

APIs de previsão:
- CONSULTANT, MANAGER, REGIONAL_MANAGER ou ADMIN conforme ação.

API cron:
- Apenas chamada autorizada com CRON_SECRET.
